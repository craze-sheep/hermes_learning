# Researcher: GitHub Project Fact-Checking Workflow

When the Supervisor assigns a fact-checking task about a software project (e.g., "verify claims about tool X"), follow this structured workflow.

## Step 1: Locate the Repository

### GitHub API Search
```
https://api.github.com/search/repositories?q=<project_name>&per_page=10
```
Returns JSON with: `full_name`, `description`, `stargazers_count`, `language`, `created_at`, `topics`, `html_url`.

**Key pitfall:** The user may cite a wrong org/repo (e.g., `nicepkg/cc-connect` when the real repo is `chenhg5/cc-connect`). Always search broadly — don't assume the user's repo path is correct.

### Direct Repo Navigation
Navigate to `https://github.com/<org>/<repo>` to confirm existence. A 404 means the claimed repo doesn't exist.

## Step 2: Extract README Content

The README is the primary source for feature claims. Extract it via browser JS:

```javascript
const rd = document.querySelector('article.markdown-body');
const text = rd ? rd.innerText : 'README not found';
```

### Searching for Specific Claims
Use JS string search to verify each claim:

```javascript
// Check if a feature is mentioned
const idx = text.indexOf('feature_name');
const context = idx !== -1 ? text.substring(Math.max(0, idx - 100), idx + 300) : 'not found';

// Check multiple terms at once
const terms = ['@all', 'group_id', 'multi-agent', 'config.toml'];
const results = {};
for (const t of terms) {
  const i = text.indexOf(t);
  results[t] = i !== -1 ? text.substring(Math.max(0, i - 50), i + 200) : 'not found';
}
JSON.stringify(results);
```

## Step 3: Verify Configuration Format

Users often provide config examples that look plausible but are fabricated (especially if generated by AI). Verify against actual sources:

1. **Check for example config files** in the repo:
   - `config/config.toml.example`
   - `config.example.toml`
   - `config/config.go` (Go projects often define config structs)

2. **Check INSTALL.md or docs/** for documented config format:
   - `https://raw.githubusercontent.com/<org>/<repo>/main/INSTALL.md`
   - `https://github.com/<org>/<repo>/tree/main/docs`

3. **Compare field by field** — create a table:
   | User's claim | Actual format | Match? |
   |---|---|---|
   | `[[agents]]` | `[[projects]]` | ❌ |
   | `type = "claude-code"` | `type = "claudecode"` | ❌ |

## Step 4: Verify Feature Claims

For each feature the user claims exists:

1. **Search README** for the feature term
2. **Search docs/** directory for detailed documentation
3. **Check issues/discussions** for community confirmation
4. **Mark each claim** as ✅ verified, ❌ debunked, or ⚠️ unverified

Common fabrication patterns (AI-generated content):
- Config keys that don't exist in the actual codebase (`group_id`, `cmd`)
- Feature names that sound plausible but aren't documented (`@all`)
- Correct project name but wrong org (`nicepkg/` vs actual `chenhg5/`)
- Mix of real features with invented configuration details

## Step 5: Write Verification Report

Structure the report as a comparison table with clear verdicts:

```markdown
| 核实项 | 结果 | 说明 |
|--------|------|------|
| 项目存在性 | ✅ | org/repo, N stars |
| 功能X | ✅/❌ | evidence |
| 配置格式 | ❌ | actual format is ... |
```

### Evidence Rules
- Every ✅ must cite a source URL or specific README text
- Every ❌ must show what the actual state is
- ⚠️ means "could not verify" — not "probably false"

## Pitfalls

1. **Assuming the user's repo path is correct** — Always search first. AI-generated content often gets the org wrong.
2. **Trusting config examples without verification** — `[[agents]]` with `name`/`type`/`cmd` fields is a common AI fabrication pattern for TOML configs. Always check the actual repo.
3. **Missing the `@all` check** — Search for exact strings including special characters. `@all` may be `@all`, `@ everyone`, or not exist at all.
4. **Not checking docs/ directory** — Some features are documented only in docs/, not in README.
5. **GitHub API rate limits** — Without auth, you get ~60 requests/hour. Use browser navigation for individual repos; reserve API calls for search.
6. **Binary/Go config structs** — Go projects may not have `.toml.example` files. Check `config/config.go` for struct definitions that reveal the actual config schema.
